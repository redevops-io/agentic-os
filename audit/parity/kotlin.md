## What it is
A JVM/Spark portability port of the ReDevOps platform (README.md): the three runtimes (context-runtime, mission-runtime, discovery-runtime), execution-planner, redevops-rag, capability-sdk, identity (permission plane), runtime-observability, runtime-spark, runtime-service (small HTTP-shaped facade), runtime-testkit. Parity target in its own README is the "contextos"/runtime-contracts Python line plus Go. Inside mission-runtime there is a `mission/kernel/` package that is a PARTIAL port of the agentic-os Python mission kernel (agentic_os/mission/*): approval.py (tokens, hash, replay guard), api_gate/control_auth, compensation*, failure policy, fork_join, rehydrate, verify, secrets bootstrap (file only). It is NOT a port of the whole kernel: there is no run loop with parking, no assurance, no durable event store, no secret/credential subsystem. The executor (mission/MissionRuntime.kt) is the older Spark-profile topological executor with an optional `KernelBinding` (opt-in; default null = legacy behaviour with no policy/saga).

## B4 cross-language canonical JSON risks (if the chain were ported using the existing Json.canonical)
Kotlin kernel/Json.kt is carefully Python-compatible for `json.dumps(sort_keys=True, separators=(",",":"), default=str)` (approval hash), including code-point key ordering (:27-31), Python float repr (pyFloat :84, exponent form, -0.0, NaN/Infinity), \u escaping of every char outside 0x20-0x7e (:74), surrogate pairs by UTF-16 unit (matches Python ensure_ascii), default=str fallback.
Concrete risks for the EVENT CHAIN:
1. The chain uses `ensure_ascii=False` (store.py:70-71) and UTF-8 bytes; Json.canonical is ensure_ascii=True. Reusing it would give different hashes for any non-ASCII payload (e.g. "é", emoji, CJK names). Need a second writer mode that emits raw UTF-8 and escapes only `"`, `\`, and control chars < 0x20 (Python with ensure_ascii=False escapes 0x7f? No: it leaves 0x7f raw; Json.kt escapes it).
2. The approval hash (approval.py:65-66) uses default ensure_ascii=True, so the two Python paths differ; Kotlin has only the one.
3. Int vs float: Python keeps `1.0` as a float (prints "1.0") and ints unbounded. Kotlin parse yields Long/Double (Json.kt header); integers > Long (BigInteger) and floats that are integral (1e16 -> Python prints 1e+16, 10**16+1.5 -> 1.0000000000000002e+16) rely on pyFloat; a JSON round trip through any other parser (Jackson, kotlinx) that turns 1.0 into 1 would silently change the hash. `ts` is a Python float (time.time(), microsecond-ish digits): the Kotlin store must carry it as Double and format via pyFloat, never via BigDecimal or toString.
4. Key order: Python sorts str keys by code point; Kotlin implements that. Non-string map keys: Python json raises or coerces int keys to str BEFORE sorting (sort order of 10 vs 9 differs after coercion), Kotlin sorts after toString: same. Duplicate keys after toString collapse differently (first wins in Kotlin `first{}` vs last wins in Python dict); edge case.
5. `default=str`: Python str() of datetime/Decimal/set/Path/bytes vs Kotlin toString(); not byte-compatible for non-JSON types (e.g. Python set repr `{'a'}`, Kotlin `[a]`). Payloads must be restricted to JSON types.
6. Sequence numbering/ts: Python seq starts at 1 per ... (global store counter, see store.py:169-212) and prev is per-mission; Kotlin seq starts at 0. Must mirror exactly or hashes diverge.
7. Hash input is `prev.encode("ascii") + b"|" + canonical`; first event has prev "" (so the input begins with "|").
8. NaN/Infinity: Python emits bare NaN (invalid JSON) and Kotlin copies it; fine for hashing but other readers reject it.

## Top risks
1. Forward-approval binding (B1), forward TTL (B5) and durable replay (B3) are absent: Kotlin can verify a token but nothing parks, digests, invalidates or persists replay state; in-memory ReplayGuard resets on restart and is per replica.
2. No mission event hash chain, no receipt head (B4); the only chain (HashChainLedger) is formula-incompatible and does not cover payloads, so Python and Kotlin audit logs cannot be cross-verified; reusing Json.canonical would also mismatch on non-ASCII (ensure_ascii).
3. Any thrown exception = clean failure that triggers compensation (B8, #526 equivalent), and no secrets/credential broker subsystem (B10) so Kotlin must rely on env/file secrets.
