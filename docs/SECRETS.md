# Platform secrets

The platform needs three secrets. They are **generated for you** (random, correct format) the first time you run
`agentic-os up`, `agentic-os-projects`, `agentic-os secrets init`, or `deploy/apps/bootstrap-secrets.sh`. A value that
already exists (environment, secrets file, keyring or Vault) is **never overwritten**. Real values are never printed
by `init`, logged, or written into shell rc files.

| Secret | Purpose / consumers | Format | Generated as |
|---|---|---|---|
| `AGENTIC_OS_APPROVAL_SECRET` | Signs/verifies approval tokens ([SECURITY_MODEL.md](SECURITY_MODEL.md#signed-approval-tokens-http-operators)). Mission runtime **and every HTTP operator**. | >= 32 chars | `token_hex(32)` (64 hex) |
| `TWENTY_APP_SECRET` | Twenty CRM JWT signing secret. | >= 32 chars, not containing `demo-only` | `token_hex(32)` |
| `OUTREACH_BASIC_AUTH` | Operator Basic-auth gate on the revenue-agent / console real actions (real sends). | `user:password`, password >= 20 chars | `operator:` + `token_urlsafe(24)` |
| `PERMISSIONS_ADMIN_KEY` | Grant-write key for the permissions plane / public permissions demo ([SECURITY_MODEL.md](SECURITY_MODEL.md#permissions-plane--access-control-admin)). Unset or invalid = writes are simulated per visitor, never open. Generated by the stack repo's `secrets` role and `bootstrap-secrets` scripts (not yet by `agentic-os secrets init`). | 64 hex chars | `token_hex(32)` |

## Where each secret is stored

Read precedence: process env > secrets file > OS keyring > Vault (if configured). `init` skips a secret found in any.

| Platform | Primary store | Shell / process availability | Extra |
|---|---|---|---|
| Linux | `~/.config/redevops/secrets.env` (dir 0700, file 0600) | managed block in `~/.bashrc` that *sources* the file | Secret Service keyring mirror (if `keyring` installed) |
| macOS | same path | managed block in `~/.zshrc` (and `~/.bash_profile` if present) | Keychain mirror |
| Windows | `%APPDATA%\redevops\secrets.env` (ACL: current user) | user-level environment variables | Credential Manager mirror |
| Vault / cloud | KV v2 mount `vibexgen`, path `agentic-os/stack` (overrides `VAULT_MOUNT`, `REDEVOPS_VAULT_PATH`) | fetch at deploy time | selected when `VAULT_ADDR` + `VAULT_TOKEN` are set, or `--backend vault`; only missing keys are added, other keys are kept; if Vault is unreachable `init` fails (no local fallback) |
| Containers | pass the file: `docker compose --env-file ~/.config/redevops/secrets.env up -d` | never generated inside a container | every operator needs the same approval secret |

Override the file location with `REDEVOPS_SECRETS_FILE`. The rc block is bounded by
`# >>> redevops secrets (managed) >>>` / `# <<< redevops secrets (managed) <<<`; the rc file is backed up once to
`<rc>.bak-redevops`. Skip it with `--no-shell-profile`.

## CLI

```
agentic-os secrets init [--backend auto|file|vault] [--dry-run] [--no-shell-profile] [--yes]
agentic-os secrets list                 # name, present, where, valid / weak reason (no values)
agentic-os secrets get NAME [--decode] [--as-header]
agentic-os secrets rotate NAME [--yes]
agentic-os secrets push [--to vault] [--only NAME ...] [--dry-run] [--yes]
agentic-os secrets where
```

## Fetch and decode

- `agentic-os secrets get AGENTIC_OS_APPROVAL_SECRET`
- `agentic-os secrets get OUTREACH_BASIC_AUTH --decode` prints `user` and `password`; `--as-header` prints
  `Authorization: Basic <base64>`. `--decode` also base64-decodes names ending in `_B64`.
- Raw equivalents: Linux/macOS `grep '^NAME=' ~/.config/redevops/secrets.env`; Vault
  `vault kv get -mount=vibexgen -field=NAME agentic-os/stack`; macOS
  `security find-generic-password -s redevops -a NAME -w`; Windows PowerShell
  `[Environment]::GetEnvironmentVariable('NAME','User')` or Credential Manager (service `redevops`).

## Override with your own value

Export it before the first start (env is respected, never replaced), or edit the `NAME=value` line in the secrets
file, or `vault kv patch -mount=vibexgen agentic-os/stack NAME=value`. Then restart the services using it and check
`agentic-os secrets list` (it flags values that are too short or contain `demo-only`).

## Push local secrets to Vault

`agentic-os secrets push` copies managed secrets that exist locally (env, secrets file, keyring) into the Vault
bundle (mount `vibexgen`, path `agentic-os/stack`; needs `VAULT_ADDR` + `VAULT_TOKEN`). It adds ONLY keys missing
in Vault: it reads the bundle, merges, and writes with check-and-set on the version read (a concurrent change is
re-read and retried, never overwritten). Existing Vault values and unrelated keys are untouched and reported as
skipped. If Vault is unreachable or denies access it fails with no local fallback. Values are never printed.
Use `--dry-run` to preview and `--only NAME ...` to limit; it prompts unless `--yes`. To reuse an exported
approval secret: `export AGENTIC_OS_APPROVAL_SECRET=...; agentic-os secrets push --only AGENTIC_OS_APPROVAL_SECRET`.

## Rotate

`agentic-os secrets rotate NAME` prints the consequences and asks for confirmation (`--yes` in scripts).

- `TWENTY_APP_SECRET`: all Twenty sessions and API keys are invalidated; log in again and recreate `TWENTY_API_KEY`.
- `AGENTIC_OS_APPROVAL_SECRET`: must be identical on the runtime and **all** operators; restart them all. Tokens
  minted with the old value stop verifying.
- `OUTREACH_BASIC_AUTH`: update every caller of the real actions; restart revenue-agent and console.
- `PERMISSIONS_ADMIN_KEY`: restart `permissions-api`/control-plane; update admin clients holding the old key.

## Back up

Copy the secrets file (or the Vault path) to an encrypted location; do not commit it or paste it into tickets. Losing
`TWENTY_APP_SECRET` logs everyone out of Twenty; losing the others only requires re-running `init` and restarting.

## Troubleshooting

- **Approved actions stay pending/staged**: the operator ignored the approval token because
  `AGENTIC_OS_APPROVAL_SECRET` is missing or differs between runtime and operator (operators log a WARNING pointing
  here). Run `agentic-os secrets init`, start every service from the same secrets file, restart runtime + operators.
  Processes started without your shell env still read the secrets file for this one secret.
- **401 on console real actions**: missing/stale `OUTREACH_BASIC_AUTH`. Send
  `agentic-os secrets get OUTREACH_BASIC_AUTH --as-header`'s header and make sure the container received the variable.
- **Vault errors**: `init` never falls back to local storage; fix `VAULT_ADDR`/`VAULT_TOKEN` or pass `--backend file`.

## Mission input values and the ledger

`MissionCreated` records a launcher-selected mission's input KEYS and an `inputs_sha256` digest, never the values (inputs may hold customer data, and the ledger is append-only). `MissionRuntime.rehydrate(mission_id, inputs=...)` must be re-supplied the values and verifies them against the digest (mismatch raises `ReplayError`); without them the selected node fails with `inputs_unavailable` rather than running with partial scope. Setting `AGENTIC_OS_RECORD_MISSION_INPUT_VALUES=1` records the values in the immutable ledger instead (replay becomes self-contained, but the values can no longer be erased and appear in anything that projects the ledger); enable it only for non-personal inputs.

## Secret references and the tenant

A secret reference (`backend:namespace/path`, for example `file:llm/provider`; `env:NAME` has no namespace) names where a secret lives, and
`agentic_os.secrets.resolve.read_secret` reads it through the credential broker on every use. runtime-contracts v0.3.15 and later refuse a
credential request unless the request tenant equals the tenant of the authority's principal **and** the reference's namespace equals that tenant
(`TENANT_MISMATCH`), the authority has not expired (`AUTHORITY_EXPIRED`) and the request names the authority (`AUTHORITY_MISMATCH`).

`read_secret` takes its tenant from one of three places, in this order:

1. the `tenant` argument, used as given (an embedding caller names it; nothing in this edition authenticates a principal for `read_secret`); an empty or malformed tenant is refused;
2. `REDEVOPS_LOCAL_TENANT`, when the deployment sets it: every namespaced reference must then live in that namespace (`env:` references are read as that tenant);
3. otherwise the single-user rule: the local user is the only tenant and a reference's namespace is that user's tenant, so `file:llm/provider` is read as tenant `llm` and `env:NAME` as `default`.

`store_secret` follows the same tenant: a reference outside it is refused and nothing is written. A reference may not contain a backslash or a
non-printable character.

The single-user rule separates nothing between the namespaces of one user's store; it reads any reference the local user configured. This
edition has no tenant identity: `REDEVOPS_LOCAL_TENANT` pins one local tenant for a single deployment, so that a reference in another namespace of
the same store is refused. It is not tenant isolation (tenant isolation is an Enterprise capability, [EDITION_BOUNDARY.md](EDITION_BOUNDARY.md), B1).

**A refusal and an unreadable key.** A refusal returns no value and logs the reason code and the reference (never the secret). When the
model-provider settings name a key reference (`key_ref`) that cannot be read (refused by the gate, absent, locked), `llm_api_key` raises
`LLMKeyUnavailable`: no request is sent, `governed_text` returns `None` and logs `model call not made`, and the provider test call reports
`LLMKeyUnavailable`. With no `key_ref` the behaviour is unchanged: `OPENAI_API_KEY`, else the placeholder `EMPTY` for a keyless local server.

**Known limitations** (the independent review, `review-read-secret.md`; each is stated, not hidden):

* `env:NAME` references have no namespace, so any environment variable of the process can be named, whatever the pin; the settings file and an approved Sidekick change are the only ways to name one.
* `read_secret` issues its own one-call authority: it carries no expiry (the 60-second grant bounds it) and its scope and authority id come from the call itself, so on this path `AUTHORITY_EXPIRED`, `AUTHORITY_MISMATCH` and the scope check cannot fire. The gate is a consistency check there, not authentication. Authority expiry is checked when the grant is issued, not at redemption.
* The store implementations in runtime-contracts resolve a symlink inside the store root before the confinement check, so a link that a local user places across namespaces is followed; on case-insensitive file systems (macOS, Windows defaults) the namespaces `Acme` and `acme` share storage. Both need write access to the store and are reported upstream, not changed here.
* `REDEVOPS_LOCAL_TENANT` and the `tenant` argument have an effect only with runtime-contracts >= 0.3.15; the pin in `pyproject.toml`, `packaging/git-pins.json` and `uv.lock` (checked by `tests/test_packaging_pins.py`) is what guarantees it.
* `ConnectionManager` and `ServiceIdentityBroker` keep their secrets in feature namespaces (the connection's domain, `identities`) and read the stores directly; the credential gate does not apply to them there. Through the mission `Executor`, an authority whose tenant is a real tenant is refused for those references (`TENANT_MISMATCH`), because the namespace is not that tenant; making the namespaces per-tenant is a prerequisite for multi-tenant use of these stores.
* The Windows path-separator case of `parse_ref` (a backslash) is rejected by construction and was analysed with the Windows path rules, not run on a Windows host.
Tests: `tests/test_read_secret_tenant.py`, `tests/test_credential_gate_shipped_paths.py`, `tests/test_read_secret_review_hardening.py`, `tests/test_llm_key_via_broker.py`.
