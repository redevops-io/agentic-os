# Search relevance hook and explicit "unknown" (SR-04)

**Status: separate draft, opt-in, read-only, default OFF.** It adds no route, no write path, no network call, no dependency and no new service. With `AGENTIC_OS_RELEVANCE_UNKNOWN_AWARE` unset and no `relevance_fn`, every existing input produces the output it produced before this change (proof below), apart from the short list of deliberate non-identities.

**Read this first: hook-computed relevance is an UNVALIDATED quality signal and an unresolved keyword-stuffing limitation remains.** The current relevance scores must **not** be used for automatic publication or for high-confidence SEO recommendations. This is enforced in code where cheap: every signal that depends on a hook-computed relevance has its confidence capped at 0.5 (`HOOK_CONFIDENCE_CAP`) and carries the evidence line `relevance unvalidated: susceptible to keyword stuffing; human review required; not for automatic publication`; nothing derived from it can become an automatic, low-risk or pre-approved action. See "Residual: keyword stuffing" and "Validation gates (open)".

## What it is
`SearchObservation.relevance` ("semantic query-to-page fit, 0..1") has never been populated: the Search Console mapper (`integrations/gsc.py`) copies only what the API returns and the API returns no page text, so every live observation carries the dataclass default `0.0`. As a consequence `near_win`, `missing_page` and `emergent_intent`, which require `relevance >= 0.6` (or `0.9`), are silently suppressed on live data. Two small seams fix the two halves of that:

1. **A hook that can supply the value.** `collect_search_observations(client, site, relevance_fn=...)` (default `None`: output bit-identical to before). `agentic_os/content/relevance.py` provides `make_relevance_fn(embedder, page_text_provider)`: a deterministic similarity between the query and a page representation (title, H1, meta description and a bounded body excerpt), computed with an injected `TextEmbedder` (`market/synthetic_research/embedder.py`, provisional `BAAI/bge-small-en-v1.5`). Page text comes from an injected `PageTextProvider`; the hook never fetches anything.
2. **An explicit "unknown".** `SearchObservation.relevance_source` (default `"unset"`) records where the value came from, so "never measured" is distinguishable from "measured low". Behind the flag below, detectors report "not assessable" instead of staying silent.

## What it is not
* Not a ranking predictor. No claim is made that relevance predicts rankings, CTR or conversion.
* Not a buyer-persuasion score. Relevance is a *search-matching* quantity.
* Not a crawler, an SEO auditor or a new service. No snapshotter ships in this slice; a real `PageTextProvider` (public pages only, robots honoured, `safe_url`) needs its own approval.
* Not calibrated. The 0.6 / 0.9 detector thresholds pre-date any relevance supplier (see "Calibration caveat").

## Unknown is not low
The relevance **source is authoritative**; the numeric `relevance` field is only a value when the source says so.

| `relevance_source` | meaning | state |
|---|---|---|
| `unset` (default) with `relevance == 0.0` | nobody supplied a value; `0.0` is the legacy placeholder | **unknown** |
| `unset` with a non-zero value | a value supplied upstream by an existing integration, unlabelled | measured: judged on its number exactly as before; with the flag on its evidence says "supplied, unlabelled" |
| `unavailable:<reason>` | a `relevance_fn` ran and could not assess (`no_page_text`, `empty_query`, `page_text_provider_error:<Type>`, `embedder_error:<Type>`, `degenerate_embedding`, `degenerate_embedder`, `relevance_fn_error:<Type>`, `invalid_result`) | **unknown**, whatever number sits in `relevance` (a placeholder) |
| `embedding:<embedder>@<revision>` | a deterministic embedding similarity | measured, in [0, 1], may be low; a measured `0.0` is **low**, never unknown |
| any other label (recommended: `supplied:<label>`) | a value supplied upstream and labelled by the caller | measured |
| any source with NaN, infinity or a value outside [0, 1] | invalid | **invalid**: treated as unknown by the unknown-aware detectors; legacy numeric behaviour with the flag off is untouched |

A relevance source is parsed by ONE shared validator, `relevance.parse_relevance_source`, used by `RelevanceResult`, `apply_relevance`, every detector and the evidence renderer (see "Source validation"). Reserved prefixes are matched case-insensitively after trimming (`" UNSET"`, `"Unavailable:x"` read as unknown, never as measured low); a source the validator rejects is `invalid` and reads as unknown, never as a measured value. `RelevanceResult.value` is `None`, never `0.0`, when a result is unavailable. The hook never turns a failure into a number. `relevance_state(o)` returns `unknown` / `invalid` / `low` / `ok`.

## Flag: `AGENTIC_OS_RELEVANCE_UNKNOWN_AWARE` (default OFF)
* **OFF**: every legacy observation (source `unset` or `supplied:*`) is judged on its number exactly as before (relevance `0.0` suppresses `near_win`, `missing_page`, `emergent_intent`). The cases that differ by design are the sources the hook (or a malformed label) can produce and no legacy producer can have set, because `relevance_source` is a new field: a hook-written `unavailable:*` source (its placeholder number never drives a detector; it would otherwise produce a signal that says both "relevance 0.90" and "unknown") and an `invalid` source (malformed, over-long or synthetic-labelled such as `ssr:buyer-score`): the number is not trusted, the detector stays silent, and with the flag on it reports "not assessable".
* **ON**: a detector that needs relevance and gets an *unknown* or *invalid* relevance returns a `WATCH` signal (same `signal_type`, confidence `0.0`) whose first evidence line is `not assessable: relevance unknown`, followed by the source and the relevance-independent facts that made the observation worth judging (impressions, position band, non-canonical page, new pairing). It is only emitted when everything *except* relevance already qualifies, so it does not create noise. A `WATCH` is never an action: `content_intervention_queue` counts it under "watching" and every real recommendation still goes through the approval-gated queue (PROPOSE only, `CONSEQUENTIAL`). `ctr_opportunity` and `cannibalization` do not use relevance and decide exactly as before.
* **Existing integrations that supply a value with the default source** (`relevance=0.8`, source `unset`) are *not* demoted with the flag on: a non-zero unlabelled value is a supplied, measured value and behaves as today (the evidence notes it is unlabelled). Only the legacy default `0.0` with source `unset` is unknown. Recommendation: label supplied values (`relevance_source="supplied:<label>"`); an upstream value that is deliberately `0.0` must be labelled too, or it reads as unknown.
* Changing the default to ON is a behaviour change and needs its own approval.

## Where unknown is distinguished (pipeline and consumers)
| Stage | Treatment of unknown / measured low |
|---|---|
| `SearchObservation` construction / `to_observation` | default source `unset`; a hook-written `0.0` carries `embedding:*`, so the two observations are never equal |
| `collect_search_observations(..., relevance_fn)` | `None` fn: untouched. A failure, `None`, NaN, out-of-range, non-numeric or non-embedding source, or a result object whose attributes raise, becomes `unavailable:<reason>` (with the embedder provenance when the hook supplied it), never a value. Reserved prefixes are canonicalised to lower case |
| `relevance_state(o)` | `unknown` / `invalid` / `low` / `ok`; explains why a relevance-gated detector stayed silent |
| `near_win`, `missing_page`, `emergent_intent` | flag off: unknown and low are both silent (as before). Flag on: unknown/invalid gives WATCH "not assessable: relevance unknown"; low gives no signal; ok gives the normal signal |
| `ctr_opportunity`, `cannibalization` | decisions unchanged; evidence states the relevance source (hook-written sources always; every source when the flag is on); cannibalization lists each competing page's reading and notes a measured/unknown mix |
| `search_signals_from_observations` | differing readings of the same (site, page, query) (two measured values, or measured next to unknown) yield a WATCH `RELEVANCE_CONFLICT` signal listing every reading; a `near_win` PROPOSE that depends on a conflicted labelled reading is held at WATCH. Legacy `unset` rows never take part. Nothing is averaged or overwritten. Active when the flag is on, or for groups containing a hook reading |
| `content_intervention_queue` | only PROPOSE signals become candidates, so not-assessable and conflict WATCH signals are never actions; counted in `watching` and broken out as `not_assessable` / `relevance_conflicts` (keys present only when non-zero) |
| `content/portfolio.py` `scan_portfolio` | rollup gains `total_not_assessable` / `total_relevance_conflicts`, only when non-zero (otherwise unchanged) |
| `growth/goals.py` (`measure_*`) | read query, page, position, impressions and CTR only: goal progress is identical whatever the relevance source (tested). `RELEVANCE_CONFLICT` advances no goal |
| `growth/loop.py`, `content/portfolio.py` `scan_site` | call `collect_search_observations` without `relevance_fn`: observations stay `unset`; flag off is identical; flag on reports "not assessable" for the default `0.0` |
| `sidekick/catalog.py` | a code reference string only |
| Projects UI tab | fetched at build time; not verifiable here |

### Conflicts, precisely
The key is `(site_id, page_url, the exact sanitised query text)`: different queries (including every non-Latin query) never conflict, and one tenant's reading is never attributed to another. Readings that differ by less than 1e-9 are the same reading. Equal values from *different* embedders or revisions are not a conflict (the claim agrees; the provenance differs, and both readings are listed if another reading conflicts). The signal does not depend on input order.

## Provenance
Every `RelevanceResult` records `embedder_name`, `embedder_revision`, the similarity map, `page_text_hash` and `query_text_hash` (SHA-256 of the exact sanitised texts embedded; never the text) and the text policy id (`visible-text-v2`). The embedder revision is the `embedder_revision` argument, else the embedder's own `revision` attribute, else a behavioural fingerprint `probe:<sha256[:12]>` of the embedding of a fixed probe string. If the probe fails the result says `revision=unrecorded` with `provenance_incomplete=true`; the failure is remembered for `probe_retry_seconds` (default 30 s, capped at 300 s, injectable clock) so a permanently failing embedder costs one extra probe call per interval, not one per row, and a later success repairs the revision. The same probe embeds a second, unrelated text: an embedder that returns the same vector for both is reported as `unavailable:degenerate_embedder`. Embedder name, revision and sources are sanitised (no control, zero-width or bidi characters, 120-character cap).

The observation keeps this in `relevance_detail`. Hook-written sources add a `relevance provenance: ...` (embedding) or `relevance unknown: ...` (unavailable) evidence line to every signal that observation produces, including `ctr_opportunity` and `cannibalization`; with the flag on every signal states its relevance source.

## Method and the cosine map
Cosine similarity `c` of the query and page-representation embeddings, mapped to [0, 1] by a monotone map recorded in every result:
* `clamp01` (default): `max(0, c)`.
* `halfcosine`: `(1 + c) / 2` (as in the SSR reference code); provided for comparison only.

The page representation is title, H1, meta description and a bounded body excerpt, each sanitised and passed through `collapse_repeats` (drops every token that completes a word 3-gram already seen in that part, so a verbatim repeated sentence, list or run counts once). The relevance function is **single-flight**: concurrent identical requests share one in-flight call (one provider call per page and one embed call per distinct text; key = embedder name + configured revision + normalised text hash). The cache lookup and the registration of a flight are one atomic step and the cache write happens inside the flight, so duplicate calls are not expected under any thread interleaving: stress tests (16-24 threads at a 1-microsecond switch interval) and the reviewer's probe saw none, but this is an empirical result, not a proof. Waiters receive the leader's result or the same failure. The leader always removes its flight, even when a `BaseException` interrupts it, and waiters are woken with an explicit `interrupted` outcome.

**Staleness and double execution.** A flight is replaced by the next caller only when its leader thread is dead, or (threaded flights only) when it is older than the timeout plus a margin. An *inline* (`thread_affine=True`) flight is **never** replaced by age: a slow but healthy call is executed exactly once, never twice or concurrently, and concurrent callers of the same key simply stop waiting after `call_timeout_seconds` with `unavailable:page_text_provider_timeout` while the leader finishes and caches its result. A threaded call that does not finish in time is abandoned (leader and waiters get `unavailable:..._timeout`, the late result is discarded and never cached); while that abandoned worker is still alive a new request for the SAME key is refused as `unavailable:..._busy` instead of running the call concurrently with its own hung worker, so a hung call can keep only its own key busy.

**Circuit breaker (per dependency: embedder, page provider).** One slow key must not suppress unrelated keys, so a timeout is first remembered for THAT key only (the per-key failure cache, `failure_ttl_seconds`, default 30 s, capped at 300 s). The dependency breaker opens only when the dependency looks down: 5 consecutive timeouts on DISTINCT keys with no response in between (`breaker_threshold`), or at least 50% timeouts among the last 20 executed calls. The first open period is 1 s (`breaker_base_seconds`), doubled after each failed trial up to 300 s. While open, cache misses get `unavailable:embedder_circuit_open` / `unavailable:page_text_provider_circuit_open` (never a zero) and cache hits are still served. After the period the breaker is half-open: exactly ONE trial call is allowed, every other key fails fast while it runs, the first response (success or an ordinary error) closes the breaker and resets its counters, a timed-out trial re-opens it with the doubled period. Only the leader's outcome counts, so waiters that stop waiting never trip it. Measured (1,000 pages, fake clock 10 ms per row, call timeout 20 ms): one isolated slow page 0 healthy pages suppressed at any TTL and any row (the round-5 design suppressed 899 of 999); 1% slow pages 0 (was 729 of 990); 5% slow pages 0 (was 949 of 950); flapping (outages of 60 and 40 rows) 110 of 900 (12%, was 700 of 900); a persistent outage costs 8 provider calls in 1,000 rows. Abandoned worker threads are counted (`cache_info()['abandoned_threads']`) and capped at `max_abandoned_threads` (default 64): only when more than 64 calls are simultaneously still hung are new calls refused with `unavailable:..._busy`, which can then also affect healthy keys (for example 100 hung pages in 1,000); that is the price of a bound on threads.

**Threads.** By default every call runs on a fresh daemon worker thread so it can be abandoned on timeout; this breaks thread-affine providers or embedders (a `sqlite3` connection created on the caller thread, a GPU context bound to one thread). With `thread_affine=True` calls run in the caller's thread: nothing can be abandoned, so the call timeout is NOT enforced for the leader (waiters still stop waiting after it), the circuit breaker cannot protect against a hung dependency, and no worker threads are created. In that mode a `KeyboardInterrupt` / `SystemExit` raised by the provider or embedder propagates to the caller (after the flight is cleaned up and nothing is cached); ordinary exceptions stay explicit `unavailable:...` results. In the default threaded mode a base exception inside a worker cannot propagate and becomes an explicit `unavailable:...` result. Failures (probe, provider, embedder, timeout, `no_page_text`) are cached per key for `failure_ttl_seconds`; both caches hold at most `cache_size` entries, so memory does not grow with repeated failures. Build a new function for each collection run so page text is never stale.

### Calibration caveat
With `bge-small-en-v1.5` unrelated text still has a cosine of roughly 0.35-0.6, so `halfcosine` maps *every* pair to at least 0.68 and would clear the 0.6 threshold for unrelated pairs. `clamp01` keeps unrelated pairs mostly below 0.6, but one unrelated pair in the tiny sanity set reached 0.603. The thresholds are unvalidated against any real data; see `docs/evidence/search_relevance_sanity.yaml` (Illustrative/synthetic, 12 queries x 6 pages, author-written).

### Residual: keyword stuffing
**This is an unresolved quality limitation, not a solved problem.** A page that literally contains the query text scores as relevant to it; that is what a semantic-similarity measure does, and `collapse_repeats` does not fix it. Measured with `bge-small-en-v1.5` and `clamp01` on the author-written set (illustrative, n = 12 queries): an honest page scored a mean 0.517 (2 of 12 queries at or above 0.6); the same page with every query pasted into its body scored 0.624 (8 of 12) before and 0.613 (8 of 12) after `collapse_repeats`, and 0.608 (7 of 12) with each query pasted once. **The current relevance scores must not be used for automatic publication or for high-confidence SEO recommendations.** Enforced in code: signals that depend on a hook-computed relevance have their confidence capped at `HOOK_CONFIDENCE_CAP = 0.5` (below the default `PriorityPolicy.min_confidence` of 0.55, so under the default policy a hook-derived PROPOSE signal ABSTAINS from the action queue: `content_intervention_queue` reports `count` 0 for it, although the signal itself is still listed with its evidence; an operator who deliberately lowers the bar still gets only `REQUEST_APPROVAL` for a `CONSEQUENTIAL` candidate, never auto, low-risk or pre-approved) and carry the evidence line `relevance unvalidated: susceptible to keyword stuffing; human review required; not for automatic publication`. Confidence for legacy and supplied relevance is unchanged. The exposure is also bounded because `near_win` requires impressions and a position in the 5-20 band (an attacker needs an existing ranking), but do not treat a high relevance as evidence that a page is honest.

## Untrusted page text
Page text is untrusted input. Before embedding it is reduced to plain text, length-bounded (title 300, H1 300, meta 500, body excerpt 2000, query 300 characters by default), and stripped of control, zero-width, bidirectional and other format characters (Unicode categories Cc, Cf, Cs, Co, Cn; separators become a space). `page_text_from_html` is a helper for providers holding raw HTML: it keeps visible text only (drops script/style/noscript/template/svg, comments and elements hidden by `hidden`, `aria-hidden="true"` or inline `display:none`/`visibility:hidden`). It is linear-time: a hidden-depth counter and a per-tag open count replace stack scans; input is capped at 200,000 characters, nesting at 256, start tags at 20,000 and collected text at 100,000 characters, beyond which the document is truncated. Hostile nesting finishes in well under a second (tested) and the helper never raises. The text is only ever embedded: never executed, never interpreted as instructions, never put in a prompt. The hook makes no chat-model call and no network call; the only external call is `embedder.embed`, and the in-boundary rules of `HttpEmbedder` still apply.

## SSR buyer scores are never relevance
Synthetic buyer research (SSR, see `docs/SYNTHETIC_RESEARCH.md`) measures buyer resonance with synthetic respondents. It is a different construct with separate code paths and labels, and is never an input to `relevance`, rankings, detector thresholds or any measured-conversion field.

The guarantee is **architectural**: `relevance.py` has no import path to the SSR scoring/study modules (a static test enforces it) and its only numeric operation is the cosine of two vectors returned by the injected embedder. **The embedder is trusted code**: a hostile embedder could encode any number as an angle between its output vectors, and no check here could detect that. The source-prefix checks (`RelevanceResult` refuses sources and embedder names with an `ssr`/`synthetic` token and any value whose source is not `embedding:`; `apply_relevance` accepts a value only from a valid `embedding:` source, decided by the shared source validator) catch accidents and mislabelling only; they add no protection against a hostile embedder.

## Evidence bridge (synthetic studies stay hypotheses)
`StudyEvidenceRef` (`market/synthetic_research/evidence_ref.py`) is a frozen, serialisable pointer to a synthetic study (study id, manifest hash, construct, embedder name, `synthetic=True`, label `HYPOTHESIS, synthetic, unvalidated`). It serialises to a `synthetic-study:v1:` string so it fits the existing `Experiment.evidence_refs` tuple with no contract change.
* `StudyEvidenceWriter` plugs into `plan_experiments(writer=...)` and labels the proposed change; study id and construct are sanitised (no newline, control or bidi characters, brackets neutralised, 80-character cap) before they are rendered.
* `attach_study_refs` accepts a planned `Experiment` only; an `Opportunity` (whose evidence is counted) or a `CommercialHypothesis` (whose evidence is sealed) raises `TypeError`.
* `plan_experiments` does not count a ref whose NORMALISED text starts with `synthetic-study:` / `synthetic_study:` (NFKC, zero-width / bidi / control characters removed, case-folded, partial look-alike fold; one shared test in `market/synthetic_refs.py`) as a supporting observation, and `freeze_experiment` raises if a hypothesis carries one, so such a ref is not sealed into an experiment's evidence. A reference that merely contains the scheme later (`obs:synthetic-study:x`) is still an ordinary, counted reference there; the first-party ledger is stricter and refuses any metric that mentions the scheme anywhere (see `docs/ledger_source_inventory.md`). The look-alike table is partial: a synthetic pointer stored under another spelling is not recognised.
* `StudyEvidenceRef.parse` raises exactly `ValueError` for any malformed input; `split_refs` returns `(first-party refs, parsed synthetic refs, malformed synthetic refs)` so one bad ref never breaks a list and is never mistaken for first-party evidence.
* `FirstPartyLedger.record` (owner decision, option B) accepts a metric only if ALL of these hold; the guard is **unconditional**: no feature flag, identical with SR-04 and `AGENTIC_OS_SYNTHETIC_RESEARCH` unset (it still refuses). (1) The object is exactly a `FirstPartyMetric`: no subclass, no duck type, no study or synthetic-response object, nothing carrying `synthetic=True`, nothing defined in the synthetic-research package. (2) `source` is exactly one of `METRIC_SOURCES` (`umami`, `gsc`, `marketplace`, `crm`, `billing`, `erp`, `analytics`): a missing, empty or whitespace source, a different case and every unregistered source (`stripe`, `ga4`, `internal`, `analytics_v2`, `umami:site`, ...) are refused; the provider-name heuristics of round 3 are gone. (3) The metric carries an **adapter attestation** minted by a registered `SourceAdapter` for that source (`market/ingestion.py`): an HMAC over a digest of every metric field and the whole provenance, so a hand-built `FirstPartyMetric(source="umami")` is refused, an attestation copied to another metric or invalidated by any mutation does not verify. (4) No field or provenance entry is a `synthetic-study:` reference (any case or whitespace). `METRIC_SOURCES` gains no synthetic source and `outcome_store.refuse_simulated` is unchanged.
  * **Honest limit:** the guard is **bypassable by code that runs in the same process**; these checks stop accidental and casual misuse. The attestation makes label-only and accidental mislabelling impossible and every first-party writer an explicit, auditable registration; keys live in a closure, adapters refuse pickling and copying, and a call with a frame of the synthetic-research package on its stack is refused. The structural protection is the import rule: no module in `market/synthetic_research` may import `outcomes_join`, `ingestion`, an adapter or the outcome store (a static test covers every module in that package).
  * **Behaviour change for out-of-repo callers (the only market-plane behaviour change of SR-04):** the base commit accepted ANY object with the right attributes, any source string (including empty, `stripe`, `ga4`, `internal`, `analytics_v2`, `umami:site`) and any provider. Now a hand-built metric, a duck-typed or subclassed metric, a non-registered or missing source and a study reference are refused; see the derived table in `tests/test_ledger_guard_compat.py`. **Migration:** register an adapter (`register_source_adapter(source, adapter_id).make_metric(...)`, example in `docs/ledger_source_inventory.md`). There is deliberately no compatibility shim: one would silently allow unknown sources. Adding a new source name needs a reviewed change to `METRIC_SOURCES`; the inventory lists every in-repo writer (none constructs a `FirstPartyMetric` outside tests) and the external sources to ask the owner about.

## Source validation (one validator)
`relevance.parse_relevance_source` is the only parser of a relevance source token. It never raises and fails closed: `None`/empty/`unset` is `unset`; a non-string, anything longer than 300 characters (never truncated into acceptance), anything containing a control, format (zero-width, bidi), separator or internal whitespace character, and anything with an `ssr`/`synthetic` token (NFKC-folded) is `invalid`. The text before the first `:` must be plain ASCII `[A-Za-z0-9_.-]` and the text after it non-empty, so a unicode lookalike of `embedding:` or `unavailable:` can never impersonate a reserved prefix; a reserved word with no colon, `unset:x`, an empty label and a duplicated or nested reserved prefix (`embedding:embedding:x`, `supplied:unavailable:x`) are `invalid`. `unavailable:` needs a reason of `[A-Za-z0-9_.:@/-]{1,200}`. An invalid source reads as unknown (state `invalid`), is shown as `<invalid>` in evidence (the raw text is never echoed), and never enters conflict logic. `tests/test_relevance_source_validator.py` covers 10,000-character identifiers, NUL/newline/bidi/zero-width, lookalikes, missing colon, empty labels, duplicated prefixes and a 30,000-sample property test that no accepted source contains an ssr/synthetic token.

## Unresolved limitations (same-process residuals and open items)
These are known and NOT fixed; none is claimed as solved anywhere in this repository.
- **Closure key recovery.** The adapter signing keys live in a closure, not in attributes; code in the same process can still recover them (introspection of the closure, `gc`, a debugger) and mint any attestation.
- **Thread-hop evasion of the frame check.** The synthetic-research caller check inspects the current call stack; handing the call to another thread (for example `gc.get_objects()` to find an adapter, then `ThreadPoolExecutor(1).submit(partial(adapter.make_metric, ...))`) is accepted by the ledger.
- **Over-block.** A call with a synthetic-research frame ANYWHERE on its stack is refused, including legitimate code that a study module happens to call from further down.
- **Keyword stuffing** (see "Residual: keyword stuffing"), **no real Search Console calibration** of 0.6 / 0.9, **no approved page-text snapshotter**, **out-of-repo ledger writers not identified**, and the **Projects UI tab** not verifiable here.
- The look-alike fold for synthetic-study references is partial and only the first 100,000 characters are examined.

## Validation gates (open)
None of these is done; nothing in this repository claims otherwise.
- [ ] Real Search Console data: relevance computed for authorised query/page pairs and compared descriptively with observed CTR and position stability on a held-out window; the 0.6 / 0.9 thresholds and the similarity map calibrated from those data.
- [ ] Page-text snapshotter approved (public pages, robots honoured, `safe_url`); until then only injected providers exist.
- [ ] Out-of-repo integrations that write the first-party ledger identified, mapped to a registered source and given an adapter (owner decision per source; see `docs/ledger_source_inventory.md`).
- [ ] Keyword-stuffing robustness: a defence beyond `collapse_repeats` evaluated on real pages (the current residual is measured on one honest page and 12 invented queries).
- [ ] Human review before any experiment or content change that relies on a relevance value (the confidence cap and the approval gate make this the only path today).
- [ ] Only after all of the above: a decision on changing the flag default.

## Validation plan (when read-only Search Console access is authorised)
Not done, and not claimed. With an approved read-only property and an approved page-text snapshotter: (1) compute relevance for the query/page pairs; (2) compare it descriptively with observed CTR and position stability over a held-out window (distribution, rank correlation, no causal language); (3) choose the map and thresholds from those data, not from this document; (4) only then consider changing the flag default. No relevance value should drive a recommendation before step 3.
