# Edge Sentinel UI audit — 2026-11-11 (fixture core, audit item P4)

Method: the dashboard was driven in a real browser against the **fixture core** (`EDGE_SENTINEL_DEMO=1`),
bound to loopback only, with operator credentials configured **and** `SENTINEL_BLOCK_ENABLED=1` so that the
authenticated kick-off is a real attempt rather than a dry run. Console errors, page exceptions and every
network response are captured, so no journey rests on "it looked fine".

Harness: `scripts/ui_audit_edge_sentinel.py` (journeys) + `scripts/run_ui_audit_edge_sentinel.sh` (server
lifecycle) + `scripts/es_serve_for_audit.py` (starts the hyphen-named app package without putting
`apps/edge-sentinel` on `sys.path`, where `operator.py` would shadow the stdlib `operator` — audit item P1).

Reproduce:

```bash
ES_PYTHON=<venv with the app's deps> UI_PYTHON=<venv with playwright> \
  scripts/run_ui_audit_edge_sentinel.sh /tmp/ui-evidence fixture
DEMO_MODE=0 scripts/run_ui_audit_edge_sentinel.sh /tmp/ui-control baseline   # control run, no fixtures
```

Playwright is deliberately **not** a dependency of the app or of the kernel: the audit runs from its own
environment, and the harness lives in `scripts/` because `pyproject.toml` maps the whole app directory into
the `edge_sentinel` wheel — a playwright-importing module there would ship to anyone who runs `pip install`.

## Defect found by this audit, and fixed

**A fixture-mode refusal surfaced as a successful HTTP 200 with a `FAILED` receipt, not as a refusal.**
With `SENTINEL_BLOCK_ENABLED=1`, `live.execute()` marks the action `FAILED` and persists that *before*
touching the edge (deliberate: a crash mid-attempt must stay retryable). `core` then refused, and the
refusal was recorded as a failed attempt. Consequences, none of which was a leak:

* the case showed "last attempt failed · retry" — a policy decision reported to an operator as an outage;
* `POST /api/cases/{id}/execute` returned **200**, and the registered `DemoRefused` → 403 handler never ran;
* a demo run left phantom retry state behind.

Nothing reached CrowdSec and `executed` was `false`, so every existing "no side effect" test stayed green —
which is exactly why the audit, not the suite, found it.

Fix: `fixture_mode.refuse_if_enabled()` is called in `live.execute()` before any state is written, and the
route re-raises `DemoRefused` instead of folding it into its generic 400 handler. Regression test
`test_an_approved_kickoff_refuses_before_any_state_is_written` asserts the refusal raises, the action is
still `APPROVED`, and **no receipt was recorded**. Dry run (`SENTINEL_BLOCK_ENABLED` unset) is untouched:
it performs no edge effect, so a demo can still walk the flow.

Verified on both levels: the unit test asserts `st.receipts == {}` and the action state unchanged, and the
browser journey asserts the reloaded page shows no failed-attempt state.

### What a refusal does *not* leave behind — checked, and reported rather than "fixed"

The question worth asking after a fix like this is whether anyone can see that the attempt happened. It
cannot, and that is the existing design rather than something this change introduced:

- `agentic_os.app_gate.deny_response()` / `denial_result()` **return** a denial
  (`{"status": "denied", "executed": False, "error": "[blocked] …"}`, `app_gate.py:378-384`). Nothing in that
  module appends to a ledger or event store — the only occurrence of "audit" in it is a docstring table cell.
- `live.decide()` records decisions (approve, reject). A fixture refusal raised before any write never reaches
  it, so it records nothing.
- Net effect: a fixture-mode refusal is observable in the HTTP response (`403 refused: demo_mode`) and in the
  fact that state is unchanged, but there is **no durable "attempted X, policy refused" record** — for demo
  mode, or for any other gate denial.

If the owner wants refusal provenance, the natural homes already exist — the case store's decision refs, or
the kernel's durable mission event ledger — and either would be a small, well-scoped change. Building one was
explicitly out of scope here, and no parallel audit mechanism has been added.


## Pre-existing findings, NOT fixed here (owner decision)

A control run (`DEMO_MODE=0`) attributes these to the dashboard, not to fixture mode. Fixture mode only
*exposes* the first one, by supplying cases where a core-less control has none.

1. **Horizontal overflow — 947px minimum content width.** Fails at 834px and 390px. Culprit is the cases
   panel: `.card__head` is `display:flex; justify-content:space-between` with no `flex-wrap`, holding the
   heading plus `GET /api/cases` pills that cannot shrink (`.pill` has no `min-width:0`). Any deployment
   **with cases** hits this on a tablet or phone. Proposed, unapplied:
   `.card__head{flex-wrap:wrap}` and `.card__head>*{min-width:0}`.
2. **Second mobile overflow at 592px caused by `table.table`** — present without fixtures too; needs a
   scroll wrapper (`.tablewrap{overflow-x:auto}`) or a stacked card layout under ~600px.
3. **No `<main>` landmark** (`h1=1`, `main=0`) — screen-reader users get no landmark to navigate to.
4. **Two tables with no caption or `aria-label`.**
5. **`window.alert()` carries the outcome** of approve/execute — it blocks the page, is auto-dismissed by
   automation, and the message exists nowhere in the page afterwards (recorded as `observed`, not `fail`).

1–4 are outside "fixture adapter + UI audit" and touch shared layout CSS, so they are reported rather than
silently changed.

## Not claimed

This audit covers one app, one browser engine, and one host. It is not cross-browser evidence (no WebKit or
Firefox run), not an accessibility conformance statement (the five a11y checks are basics: names, landmark,
`lang`, heading order, focus visibility — not WCAG), and not a responsive design review.
